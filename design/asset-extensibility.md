# 확장 설계: 노트북에서 "학습만 시키면 무엇이든" 렌탈로

11/6 강사님 브리핑 피드백 5번("노트북에 한정하지 말고, 어떤 물건이든 학습만 시키면 렌탈할 수 있게 확장성을 고려하라")에 대한 답입니다. **11/13 코드 프리즈 전에는 코드를 바꾸지 않고**, 이 설계를 과제설명서(3. 활용 방안)와 발표의 "확장" 구간에 넣습니다.

## 한 줄 요약

TRACE의 핵심인 **세 시점 기록, 등급, 해시 체인 봉인, 영수증 메일은 물건 종류와 상관이 없습니다.** 노트북에 묶인 곳은 세 군데(촬영 목록, 탐지 모델, 기종 정보)뿐이고, 셋 다 "물건 종류" 한 단계를 위에 두면 풀립니다.

## 지금 무엇이 이미 일반적인가

| 부분 | 지금 | 물건이 바뀌어도 그대로인 이유 |
|---|---|---|
| 렌탈·시점 | 출고(OUT) → 수령(RCV) → 반납(RET), 앞 시점이 봉인돼야 다음 시점 | 렌탈 흐름은 물건과 무관 |
| 해시 체인 봉인 | 시점마다 사진 해시·판정·앞 해시를 묶어 Ed25519 서명(`trace-chain-1`) | 재료가 "사진 + 판정"이라 물건과 무관 |
| 영수증 메일 | 봉인 지문을 고객 메일로 1회 발송 | 물건과 무관 |
| 흠집 클래스 | scratch·dent·crack·stain 4개 | 대부분의 단단한 물건(카메라·태블릿·게임기·공구)에 그대로 통함 |
| 모델 버전 기록 | 탐지 결과마다 modelVersion 저장 | 물건별 모델이 생겨도 기록 구조는 같음 |
| 부스 촬영 목록 | 설정(`TRACE_BOOTH_SHOTLIST`)으로 바뀜(mvp·kb·side) | 목록만 더하면 새 면을 찍을 수 있음 |

## 노트북에 묶인 세 곳과 바꾸는 법

| 묶인 곳 | 지금 | 확장 설계 |
|---|---|---|
| 1. 촬영 목록·필수 면 | 빠른 검사 필수 면이 TOP·BOT(`codes.yaml`) | 물건 종류마다 필수 면·조명 목록을 둔다. 계약에는 값 **추가**만 |
| 2. 탐지 모델 | 부스에 엔진 하나(`TRACE_BOOTH_ENGINE`) | 물건 종류 → 모델 버전 표. 부스는 고른 기기의 종류에 맞는 엔진을 쓴다 |
| 3. 기종 정보 | `rental.device_model.form_factor`가 `CLAMSHELL` 하나, 치수·사양이 노트북 기준 | `form_factor`에 값을 더하고(예: `SLATE` 태블릿, `BOX` 카메라 몸체), 사양 칸은 종류별 선택 항목으로 |

`form_factor`는 처음부터 "새 형태는 codes.yaml에 먼저 추가"하도록 만들어 둔 칸이라([ddl.md](ddl.md)), 확장은 테이블을 새로 만드는 일이 아니라 값을 더하는 일입니다.

## 새 물건을 붙이는 순서 (공식)

이번 프로젝트에서 실제로 해 본 순서가 그대로 공식이 됩니다.

1. **형태 값 추가:** `codes.yaml`에 형태와 필수 면을 추가한다(계약은 추가만).
2. **촬영 목록:** 부스 촬영 목록에 그 형태의 면·조명을 더한다.
3. **사진 수백 장:** 같은 물건 10~15대를 빌려 부스에서 찍는다(노트북은 15대·67회).
4. **라벨링:** 같은 4클래스로 폴리곤을 그린다(Codex가 그리고 사람이 검수).
5. **미세조정:** 공개 표면 결함 데이터(AI Hub 선박 도장·LNG 탱크)로 사전학습한 가중치에서 출발해 새 물건 사진으로 미세조정한다.
6. **엔진 올리기:** ONNX → Jetson TensorRT 엔진 → 물건 종류 ↔ 모델 버전 표에 등록.

서버·봉인·영수증·관리자 화면은 손대지 않습니다. 새 물건마다 드는 일은 촬영·라벨·학습뿐입니다.

## 발표·질의응답에서 쓸 말

- "봉인·등급·영수증은 물건과 상관없고, 노트북에 묶인 건 촬영 목록·모델·기종 정보 세 곳뿐입니다."
- "새 물건 = 사진 수백 장 + 미세조정입니다. 노트북에서 실제로 이 순서를 밟았습니다."
- 예상 질문 "흠집 모양이 물건마다 다르면?" → 클래스는 그대로 두고 물건별 모델을 따로 미세조정하며, 결과마다 모델 버전을 기록해 어느 모델로 판정했는지 남습니다.
