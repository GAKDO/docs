# ERD 리뷰 예상 질문과 답 (2026-11-20)

강사님 전체 리뷰에서 ERD·DB 설계에 대해 나올 만한 질문과 우리 답을 정리했습니다. 답은 지금 코드와 마이그레이션 기준이고, 근거 문서를 함께 적었습니다. 지금 스키마는 [ddl.md](../design/ddl.md), 정규화 점검은 [erd-normalization.md](../design/erd-normalization.md), 설계 규칙은 [mvp-design.md](../design/mvp-design.md#erd)의 "ERD" 절입니다.

## 30초 요약 (먼저 말할 것)

- PostgreSQL `trace` DB 하나에 **서버별 스키마 7개, 테이블 37개**입니다. 서버는 자기 스키마만 읽고 씁니다.
- **기본 키는 bigint, 밖에는 NanoID 21자 `public_id`**입니다(강사님 11/2 피드백 반영).
- **서버 사이에는 FK를 두지 않고** 상대 서버의 `public_id`를 값으로만 듭니다. 정합성은 RabbitMQ 이벤트 7종으로 맞춥니다.
- 같은 서버 안은 3NF를 지킵니다. 11/20에 다시 점검해 중복 8건을 고쳤고(2단계 마이그레이션), 서버 사이 사본은 원본 서버를 적어 둔 의도된 비정규화입니다.
- 스키마는 Flyway로만 바꾸고, "칸 추가 먼저, 삭제는 다음 배포" 규칙으로 롤백해도 돌게 합니다.

## 1. 전체 구조

**Q. 마이크로서비스인데 왜 DB를 하나만 쓰나요? Database per Service가 아니지 않나요?**
학교 서버의 PostgreSQL 한 대를 받아 쓰는 환경이라 인스턴스는 하나지만, 서버마다 스키마를 나눠 **논리적으로는 서비스별 DB**입니다. 서버는 자기 스키마만 쓰고(헌법), 다른 스키마를 조인하지 않으며, 스키마 사이 FK도 없습니다. 그래서 스키마 하나를 다른 인스턴스로 옮겨도 코드는 접속 주소만 바뀝니다. 한계도 있습니다. 지금은 DB 계정을 서버마다 나누지 않아 권한으로 막지는 못하고 규칙과 리뷰로 지킵니다. 서버별 계정(자기 스키마만 권한)은 11/8 보안 점검에서 대회 뒤 할 일로 적어 두었습니다.

**Q. capture와 inspection은 왜 스키마가 둘인데 FK가 있나요?**
둘 다 capture-server가 가집니다. 스키마는 "촬영 원본"과 "검사 결과"를 나눠 보려고 둘로 했고, 소유 서버가 같으니 FK를 씁니다. 규칙은 "스키마 사이"가 아니라 "서버 사이 FK 금지"입니다.

**Q. 테이블 37개는 어떻게 나뉘나요?**
rental 6(기종·기기·렌탈·시점·파일럿·부스 코드), capture 2 + inspection 5(세트·사진 / 정합·흠집·흠집 비교·등급·텍스처), diagnostics 7(실행·부품·배터리·SSD·벤치마크·플래그·봉인 사본), report 6(체인·리포트·옛 뷰·시점 읽기 모델·처리한 이벤트·수동 봉인), auth 8(계정·렌탈 연결·소셜·메일 토큰·봉인 영수증·부스 자격·QR 링크·페어링), ml 3(집 PC). 모든 기록의 기준점은 `rental.checkpoint`(출고·수령·반납 시점)입니다.

## 2. 키와 ID

**Q. 왜 UUID가 아니라 bigint + NanoID인가요?**
기본 키는 `bigint GENERATED BY DEFAULT AS IDENTITY`입니다. 8바이트라 인덱스가 작고(UUID 16바이트), 순서대로 쌓여 B-tree 삽입이 빠르며 디버깅 때 읽기 쉽습니다. 대신 순번은 +1로 넘겨짚을 수 있어(IDOR 위험) 밖에 내보내지 않습니다. API·이벤트·URL·JWT `sub`에 나가는 9개 표에만 `public_id varchar(21) UNIQUE`(NanoID, URL에 안전한 64글자 × 21자 ≈ 126비트)를 둡니다. 근거: [decisions.md](../decisions.md) "ID는 내부 bigint, 밖에는 NanoID".

**Q. NanoID는 앱에서 만드는데 충돌하면요?**
126비트라 실제로는 충돌하지 않지만, `UNIQUE` 제약이 마지막 방어선입니다. 충돌하면 INSERT가 실패하고 요청이 오류로 끝나며 잘못된 데이터는 남지 않습니다.

**Q. 대리 키만 있으면 같은 데이터가 두 번 들어가지 않나요?**
업무 키마다 UNIQUE를 따로 둡니다. 예: 기기 `serial`, 기종 `model_code`, 시점 `(rental_id, type)`, 사진 `(capture_set_id, face, light, camera)`, 소셜 `(provider, subject)`, 체인 `(rental_id, seq)`, 처리한 이벤트 `event_id`.

## 3. 정규화

**Q. 정규화는 어디까지 했나요?**
같은 서버 안은 3NF입니다. 모든 표가 대리 키 + 업무 키를 갖고, 한 표가 한 사실만 담으며 부분 종속은 없습니다. 11/20에 마이그레이션을 모두 적용한 실제 스키마로 다시 점검해 8건을 고쳤습니다. 대표 예는 `rental.booth_code.rental_id`입니다. 시점이 렌탈을 정하는데(`checkpoint_id → checkpoint.rental_id`) 렌탈을 또 적은 이행 종속이라 코드가 시점에서 따라가게 바꿨습니다. 목록은 [erd-normalization.md](../design/erd-normalization.md) "고친 것".

**Q. 뺄 수 없는 중복은 어떻게 했나요?**
제약으로 묶었습니다. `inspection.grade_result`는 "시점당 등급 하나"(UNIQUE) 때문에 `checkpoint_id`를 뺄 수 없어 합성 FK `(capture_set_id, checkpoint_id) → capture_set(id, checkpoint_id)`로 세트와 시점이 어긋나지 못하게 했습니다. 계산값 `battery_reading.max_capacity_pct`는 같은 식인지 CHECK로 확인하고, `defect_match.status`와 `prev_defect_id`는 `(status = 'EXISTING') = (prev_defect_id IS NOT NULL)` CHECK로 묶었습니다.

**Q. 서버 사이에 값을 복사해 둔 건 정규화 위반 아닌가요?**
의도된 비정규화입니다. 원본은 늘 한 서버에만 있고, 다른 서버는 이벤트나 토큰 발급 때 받은 값을 사본으로 듭니다. 예: `rental.checkpoint.grade`는 capture-server 등급을 `trace.checkpoint.graded`로 받은 사본으로, "문제 있는 검사만 보기"를 rental 안에서 거르려고 둡니다. `capture_set.device`는 찍은 때의 기종·치수 스냅샷입니다(나중에 기종 정보가 바뀌어도 그때 기준으로 측정해야 함). 사본마다 원본 서버를 [erd-normalization.md](../design/erd-normalization.md) "의도된 비정규화" 표에 적었습니다.

**Q. jsonb를 많이 쓰는데 1NF 위반 아닌가요?**
앱이 통째로 읽고 쓰는 값(다각형·호모그래피, 계약 조각, 서명 원문, 읽기 모델의 배열)만 jsonb로 두고 원자값으로 다룹니다. SQL이 안쪽을 조건으로 쓰는 곳은 `capture_set.skipped_faces` 한 군데뿐입니다. 안쪽 값으로 조인·검색하게 되면 그 칸부터 자식 표로 빼는 것이 원칙입니다.

**Q. `record_chain`의 `checkpoint_type`과 `seq`는 서로를 정하는데요(BCNF)?**
맞습니다. 출고 1 → 수령 2 → 반납 3이라 종류가 순번을 정합니다. 하지만 둘 다 서명하는 줄 형식 `trace-chain-1`에 들어가 있어서, 빼면 이미 봉인한 기록을 다시 검증할 수 없습니다. 해시 체인의 겹친 값(`payload`·`payload_hash`·`prev_hash`·`signature`)도 변조를 가리려고 일부러 겹쳐 둔 증거입니다.

## 4. 서버 사이 정합성

**Q. FK가 없으면 없는 렌탈 ID가 들어갈 수 있지 않나요?**
DB 차원에서는 들어갈 수 있고, 앱이 두 군데에서 막습니다. 첫째, 촬영·진단을 올리는 토큰(촬영 링크, 페어링 JWT, 부스 코드)은 관리자가 렌탈 화면에서 고른 시점으로만 발급되고, capture·diagnostics 서버는 토큰 클레임의 `rentalId`·`checkpointId`와 요청 값이 다르면 거절합니다. 둘째, 원본을 가진 rental-server가 이벤트를 받을 때 모르는 시점(`UNKNOWN_CHECKPOINT`)이나 렌탈이 다른 시점(`RENTAL_MISMATCH`)은 반영하지 않고 DLQ로 보냅니다(`CheckpointEventListener`). 솔직한 한계는, auth-server가 발급할 때 rental-server에 시점이 있는지 다시 묻지 않는다는 점입니다. 발급 화면이 rental 목록에서 고르게 되어 있어 실제로 문제는 없었지만, 서버 사이 확인 호출을 더하는 것이 더 단단합니다.

**Q. 렌탈을 지우면 다른 서버 데이터는요? CASCADE가 없는데요.**
업무 데이터는 지우지 않습니다. 기기는 `RETIRED`로 상태만 바꾸고 이력을 남기며, 계정 탈퇴는 이메일을 NULL로 비우고 행은 남깁니다. 지우는 경우는 테스트 데이터(`TEST-` 일련번호)뿐이고, rental-server가 지운 뒤 `trace.checkpoint.purged` 이벤트를 보내 각 서버가 자기 사본을 지웁니다. 서버 안에서는 CASCADE를 씁니다(예: 시점을 지우면 부스 코드도).

**Q. 이벤트가 두 번 오거나 순서가 바뀌면요?**
모든 이벤트에 NanoID `eventId`가 있고 받는 쪽이 멱등하게 처리합니다. report-server는 `processed_event(event_id UNIQUE)`로 이미 처리한 이벤트를 건너뜁니다. HTTP 쪽도 촬영 완료·검수 완료·진단 업로드에 `Idempotency-Key`를 저장해 같은 키로 다시 오면 저장한 응답을 돌려주고, 같은 키에 다른 본문이면 422입니다.

**Q. DB 커밋과 이벤트 발행이 원자적인가요? (dual write)**
완전히 원자적이지는 않습니다. Spring AMQP 채널 트랜잭션으로 DB 커밋 직후에 메시지를 확정해서, DB가 롤백되면 이벤트도 나가지 않습니다. 다만 DB 커밋과 메시지 확정 사이에 서버가 죽으면 이벤트를 잃을 수 있습니다. 규모를 키우면 **트랜잭셔널 아웃박스**(같은 트랜잭션에 outbox 표에 쓰고 따로 발행)로 바꾸는 것이 다음 단계입니다. 지금은 읽기 모델이 늦거나 빠졌을 때 원본 서버 API로 다시 맞출 수 있습니다.

## 5. 제약·인덱스·동시성

**Q. "기기 하나에 진행 중 렌탈 하나"는 어떻게 보장하나요? 동시에 두 요청이 오면요?**
부분 유니크 인덱스 `ux_rental_open_device ON rental(device_id) WHERE status = 'OPEN'`입니다. 앱에서 먼저 확인해도 동시 요청은 둘 다 통과할 수 있으므로 마지막 판단은 DB가 합니다. 같은 방식으로 "시점당 지금 진단 하나"는 `uq_run_checkpoint_current ... WHERE superseded_at IS NULL`, "렌탈당 시점 종류 하나"는 `UNIQUE (rental_id, type)`입니다.

**Q. 인덱스는 어떤 기준으로 걸었나요?**
조회 경로마다 겁니다. FK 칸(자식 쪽), 화면 목록의 거르기·정렬 칸(`checkpoint(rental_id, grade)`, `capture_set(created_at DESC)`), 일부 행만 보는 대기 목록은 부분 인덱스(`capture_set(completed_at) WHERE 검수 대기`, `seal_receipt(rental_id) WHERE sent_at IS NULL`, `checkpoint_view(status, graded_at) WHERE status = 'GRADED'`)입니다. 11/20 리뷰 준비 때 FK 칸을 다시 훑어, 기기 목록이 닫힌 렌탈까지 `rental.device_id`로 찾는데 OPEN만 덮는 부분 인덱스뿐인 것을 찾아 전체 인덱스를 더했습니다(rental V6).

**Q. 코드 값(등급·면·조명)은 왜 PostgreSQL enum이 아니라 CHECK인가요?**
값의 원본은 contracts `codes.yaml` 한 곳이고, DB는 `varchar + CHECK`로 그 값만 받게 합니다. PostgreSQL enum은 값을 빼거나 순서를 바꾸기 어렵고 트랜잭션 안에서 다루기 까다롭지만, CHECK는 마이그레이션에서 제약만 바꾸면 됩니다.

**Q. 시각은 어떻게 저장하나요?**
모두 `timestamptz`(UTC로 저장, 오프셋 포함 ISO 8601로 주고받음)입니다. 반납 예정일처럼 날짜만 있는 값은 `date`입니다.

## 6. 보안·개인정보

**Q. 개인정보는 어떻게 다루나요?**
렌탈에는 이름 대신 내부 참조 번호(`renter_ref`)를 두고 고객 이름은 선택 칸(관리자만 봄)입니다. 파일럿 참여자는 별칭(`P01`)만 두고 실명은 DB 밖에 보관합니다. 비밀번호·부스 client secret은 BCrypt, QR 토큰·페어링 코드·메일 토큰은 SHA-256 해시만 저장해 DB가 새도 원문을 쓸 수 없습니다.

**Q. 사진 같은 큰 파일은요?**
DB에는 MinIO 객체 키와 `sha256`만 둡니다. 업로드 URL에 체크섬을 서명해 넣어 다른 파일은 저장소가 거절하고, 완료 때 서버가 다시 대조합니다.

## 7. 스키마 변경과 운영

**Q. 스키마는 어떻게 바꾸나요? 롤백은요?**
서버마다 Flyway로 자기 스키마만 바꿉니다(`V<번호>__<설명>.sql`, 이미 적용한 파일은 고치지 않음). 자동 롤백은 코드만 되돌리므로 "칸 추가 먼저, 삭제는 다음 배포"로 나눕니다. 운영 gakdo.site는 학교 서버가 3분마다 `:develop` 이미지를 받아 다시 띄우므로(gitops compose `TRACE_TAG` 기본값 develop, `autodeploy.sh`) **develop 머지가 곧 운영 반영**이고, 서버가 뜰 때 Flyway가 운영 DB에 마이그레이션을 적용합니다. 그래서 11/20 정규화도 1단계(코드가 칸을 안 쓰고 NULL 허용, 11/20 develop 머지로 운영 반영)와 2단계(1단계가 운영에서 문제없이 돈 뒤 칸 삭제, 머지 전 사람 확인)로 나눴습니다. 새 제약은 `NOT VALID`로 더한 뒤 확인을 시도해, 옛 행이 어긋나도 서버는 뜨고 새 행은 늘 확인됩니다.

**Q. 문서의 ERD와 실제 DB가 같은지 어떻게 아나요?**
11/20에 서버 5개의 마이그레이션을 빈 PostgreSQL 16에 모두 적용한 DB와 [ddl.md](../design/ddl.md) SQL을 적용한 DB를 비교해, 컬럼·제약·인덱스 638줄이 같은 것을 확인했습니다. Crowfoot의 ERD v1(10/31, 30개)은 처음 설계 기록이고, 지금 기준은 ddl.md의 논리·물리 ERD 두 장입니다. 물리 ERD는 ddl.md SQL을 읽어 스크립트로 그리므로 손으로 그린 그림처럼 스키마와 어긋나지 않습니다.

**Q. 논리 모델과 물리 모델은 어떻게 다른가요?**
논리 모델([erd-logical.svg](../design/erd-logical.svg))은 엔터티 33개를 업무 말로 보이고, 식별자는 업무로 구별하는 값(공개 ID, 또는 부모 + 구별 속성)입니다. 서버가 달라도 관계는 관계로 그립니다. 물리 모델([erd-physical.svg](../design/erd-physical.svg))로 옮기면서 세 가지를 바꿨습니다. ① 모든 표에 대리 키 `bigint id`를 두고 업무 식별자는 UNIQUE로 내렸습니다(인덱스가 작고 키가 바뀌어도 FK가 안 흔들림). ② 서버 사이 관계는 FK 대신 `public_id` 값으로 두었습니다(서비스별 스키마). ③ 구현에 필요한 칼럼(생성·수정 시각, 멱등 키, 해시)과 이벤트로 받은 사본 표 4개(시점 읽기 모델 등)를 더했습니다. 그래서 엔터티 33개가 표 37개가 됐습니다.

**Q. 데이터가 많아지면요?**
가장 빨리 느는 것은 사진·흠집·진단 자식 표인데 모두 상위 행(세트·사진·실행)에 붙어 있고 그 FK에 인덱스가 있어, 시점 단위 조회는 행 수와 무관하게 짧습니다. 큰 바이너리는 DB 밖(MinIO)이고, 성능 그래프용 목록은 `created_at DESC` 인덱스로 최근 것만 읽습니다. 수백만 행 이후에는 `photo`·`defect`를 생성 월로 파티셔닝하는 것을 생각합니다.

## 약점으로 먼저 말해 둘 것

물어보기 전에 알고 있다고 말하면 좋은 것들입니다.

| 약점 | 지금 | 다음 단계 |
| --- | --- | --- |
| DB 인스턴스·계정 하나 | 스키마 분리 + 규칙으로 지킴 | 서버별 DB 계정(자기 스키마 권한만) |
| 이벤트 발행이 DB와 원자적이지 않음 | 채널 트랜잭션, 멱등 소비, DLQ | 트랜잭셔널 아웃박스 |
| 정규화 2단계가 남음 | 칸은 안 쓰고 NULL만 허용 | 1단계가 운영에서 문제없이 돈 뒤 칸·표 삭제(rental V7, diagnostics V7, report V6). develop 머지 = 운영 반영이라 머지 전 확인 |
| Crowfoot ERD가 옛 설계 | ddl.md가 기준 | 지금 스키마로 다시 가져오기 |
