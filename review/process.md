## 2. 브랜치 전략

**설계(10/31):** 블로그 프로젝트에서 쓰던 목표 단위 Git Flow를 모든 레포에 넣었습니다(각 레포 `CONTRIBUTING.md`).

| 브랜치 | 용도 |
| --- | --- |
| `feature/<번호>-<이름>` (Claude 세션은 `claude/<세션>`) | develop에서 따서 develop으로 squash 머지 |
| `develop` | 통합. PR·푸시마다 테스트와 이미지(`:develop`) |
| `main` | 릴리스 PR(merge commit)로만. `CHANGELOG.md` 버전 → `release.yml`이 태그·GitHub Release |
| `hotfix/<버전>` | main에서 따서 main과 develop에 |

**실제(11/3~):** 클러스터(Argo CD가 main을 배포)를 멈추고 학교 서버 Compose로 바꾸면서, 운영 서버가 **`:develop` 이미지를 3분마다 받아 배포**하게 됐습니다(gitops `compose/docker-compose.yml`의 `${TRACE_TAG:-develop}`, `compose/ops/autodeploy.sh`). 그래서 지금은 사실상 **develop = 운영**, main = 릴리스 기록(태그·CHANGELOG)입니다.

- 왜 그렇게 뒀나: 11/3~11/13에 하루에도 여러 번 실서버에서 확인해야 했고(부스 실기, 리허설), 릴리스 PR을 매번 거치면 확인이 하루씩 밀렸습니다. 대신 배포마다 ping의 커밋 SHA 확인과 자동 되돌리기, 촬영·시연 전 `autodeploy.sh pause`로 위험을 줄였습니다.
- 잃은 것: 운영 전에 한 번 더 보는 단계(스테이징)가 없습니다. DB 마이그레이션도 develop 머지 순간 운영에 닿습니다. 그래서 헌법의 "컬럼 추가 먼저, 삭제는 다음 배포" 규칙과 NOT VALID 제약(11/20 정규화)을 썼습니다.
- 다시 한다면: `develop → 스테이징 Compose`, `main → 운영`으로 나누거나, 지금처럼 하나라면 브랜치 이름을 trunk 방식(`main` 하나 + 짧은 기능 브랜치 + 태그 배포)으로 정직하게 바꾸겠습니다.

## 3. PR과 리뷰

- **단위:** PR 하나 = 백로그 기능 하나, 코드 400줄이 넘으면 나눕니다. 본문은 레포마다 같은 PR 틀(Summary·Why(요구사항 ID)·검증)입니다.
- **관문:** 브랜치 보호(main·develop, 강제 push·삭제 금지) + 필수 검사(서버 `test`·`secrets`, web `build`·`secrets`, contracts `lint`·`secrets`, gitops `매니페스트 검증`·`secrets`). **필요 승인 0명**(11/2 팀 결정)이라 검사가 초록이면 올린 사람이 머지합니다.
- **자동 리뷰:** CodeRabbit(한국어, 레포마다 `.coderabbit.yaml`에 우리 규칙을 리뷰 기준으로 넣음: 예 부스는 "코드 값이 codes.yaml과 같은지, 사진마다 SHA-256을 남기는지"). 머지 전에는 보안·데이터 손실·계약 위반 같은 심각한 지적만 고칩니다. 11/13까지는 PR마다 자동 리뷰가 달렸습니다(예: agent #14 지적 6건 중 5건 반영). **11/20 현재는 CodeRabbit이 '별 10개 미만 레포는 자동 리뷰 안 함'으로 바뀌어 새 PR에는 리뷰가 달리지 않습니다**(booth #71 등). 필요하면 PR 댓글 `@coderabbitai review`로 한 번씩 부릅니다.
- **계약 PR:** contracts를 먼저 머지하고 그 버전을 쓰는 PR을 서버·화면에 냅니다. contracts PR은 머지 전에 팀 단톡에 한 줄 공지합니다. 11/20에는 깨지는 변경을 CI가 막는 검사를 더했습니다([spec.md](spec.md)).
- **AI 사용:** 팀원 모두 Claude Code로 개발했습니다. 그래서 사람의 역할을 "결정과 실기 확인"으로 정했습니다. 원칙은 헌법과 각 레포 `CLAUDE.md`(계약을 바꿔야 하면 코드를 고치지 말고 멈추고 사람에게 알린다, 비밀값 금지 등), 결정은 [../decisions.md](../decisions.md)에 누가 정했는지와 함께, 동작은 구현현황 시트 D열에 "머지 + 실기·배포 확인"을 한 것만 체크합니다.

| 워크플로 | 무엇을 | 언제 |
| --- | --- | --- |
| `backend-ci` | `./mvnw verify`(테스트 + JaCoCo 40%), SonarQube(학교 서버, 실패해도 CI는 막지 않고 알림) | PR, develop push |

| `매니페스트 검증` | 비밀값 검사 + `kustomize build overlays/school | kubeconform` | PR, push |
| `배포` | 이미지 → GHCR(`:SHA`·`:develop`, main은 `:latest`) | develop·main push |
| `비밀값 검사` | 학교 공용 비밀번호 패턴 + gitleaks(이력 전체) | 모든 PR·push |
| `release` | CHANGELOG 맨 위 버전으로 태그·Release | main의 CHANGELOG 변경 |
| `운영 점검`(gitops) | 바깥에서 gakdo.site 화면·서버·인증서 확인 | 30분마다 |

- 액션은 모두 **커밋 SHA로 고정**합니다(`actions/checkout@11d5960…`), 태그를 바꿔치기하는 공급망 공격을 막기 위해서입니다.
- PR CI는 문서만 바뀌어도 돕니다. 필수 검사가 경로 필터로 건너뛰면 '대기'로 남아 머지가 막히기 때문입니다.
- 배포는 **끌어오기 방식**입니다. GitHub에 서버 접속 키를 두지 않고, 학교 서버가 GHCR에서 이미지를 받아 서비스별로 새 컨테이너를 옆에 띄우고 ① 죽지 않는지 ② ping 응답 ③ 응답의 커밋 SHA가 새 이미지인지 확인한 뒤 옛 컨테이너를 내립니다. 실패하면 새 것만 지우고 그 이미지를 '실패'로 적어 다시 시도하지 않습니다. 자세한 것은 [architecture.md](architecture.md).
- 운영 보조: 야간 DB 백업(`compose/ops/backup.sh`), 서버 안 상태 점검(`health.sh`, cron)과 바깥 점검(30분)을 둘 다 둡니다. 서버가 죽으면 서버 안 점검은 알릴 수 없기 때문입니다.

## 7. B 담당 기술 흐름

### 7-1. 부스 촬영 → 학습 데이터

```
노트북 1대 = 위(TOP)·바닥(BOT) × 조명 L1·L2·L3 × 카메라 CAM1·CAM2 = 12장
  → 사진마다 SHA-256, 파일명에 기기 publicId·면·조명·카메라
  → MinIO trace-raw 업로드(실패분은 로컬 SQLite 큐에 두고 재시도)
  → Label Studio에서 흠집 폴리곤 → ml 데이터셋 빌더(타일 640, 겹침 0.2)
```

- **11/5 하루에 MacBook Air M2 15대, 67회, 약 870장.** 흠집 수에 따라 3·5·7회 자리를 바꿔 다시 찍었습니다(정위치·회전·좌우·180°).
- **검증은 기기 단위로 뗐습니다(학습 12대, 검증 3대 MB04·MB13·MB16).** 같은 노트북 사진이 학습과 검증에 섞이면 같은 흠집을 외운 것을 성능으로 착각하기 때문입니다.
- **제외 목록**을 문서로 남겼습니다(카메라 USB가 빠져 CAM2 짝이 없는 사진 등). 한 카메라가 실패하면 그 단계 사진을 하나도 남기지 않게 부스를 고쳤습니다(booth #50).
- 조명·카메라 값(노출·게인·화이트밸런스·초점)을 프리셋으로 고정하고 v4l2-ctl로 넣은 뒤 다시 읽어 확인합니다. 학습 때와 시연 때 사진이 같아야 모델이 그대로 맞기 때문입니다.
- 한계: 학습 데이터가 전부 한 기종·한 색입니다. 시연(같은 기종 대여)에는 맞지만 다른 기종은 기종 등록과 학습 사진을 더해야 합니다(11/7 결정, [../design/asset-extensibility.md](../design/asset-extensibility.md)).

### 7-2. 학습 v001 → v004와 모델 고르는 기준

모델은 **mAP가 아니라 "이 면에 흠집이 있나"(기기 면 판정)로 골랐습니다.** 흠집이 적은 부스 데이터에서는 mAP가 판정과 따로 놀았습니다(v001 mAP50 0.184인데 기기 면 6/6). 그래서 학습에 안 쓴 검증 기기에서 부스가 실제로 내는 판정을 세는 `trace-ml evaluate`(ml #21)를 만들었습니다.

| 모델 | 바꾼 것 | 결과 | 판단 |
| --- | --- | --- | --- |
| AI Hub 사전학습만 | – | 깨끗한 면까지 오탐(기기 면 2/6) | 부스 사진 미세조정 필요 |
| v001 | 부스 사진 2에포크 미세조정 | 기기 면 6/6 | 첫 모델 |
| 100에포크 | 오래 학습 | 3/6·4/6 | 학습 기기 12대를 외움 |
| v002 백본 고정 | `--freeze 10` | 모든 자국을 scratch로 | 탈락 |
| v002 증강 6종 | 회전·밝기·mixup 등 | 흠집은 더 찾지만 깨끗한 면도 오탐 | **사람 검수 방식으로 전환** |
| **v004** | 키보드·옆면 라벨, 건너뛴 사진 처리 버그 수정(ml #32), 증강 | 흠집 면 4/4, 오탐 사진 48 → 15 | **대회 모델** |

- 같은 v004 검증셋(conf 0.25)에서 v002 증강 → v004: **정밀도 0.50 → 0.71, 재현율 0.77 → 0.60.** 사진 재현율을 내주고 오탐을 줄인 선택입니다. 11/8 원칙("놓친 흠집은 되돌릴 수 없으니 넓게 잡고 사람이 지운다")과 어긋나 보이므로, 답할 때 반드시 함께 말합니다: **흠집 있는 면은 v004도 4/4를 모두 잡았고(v002 증강은 3/4), 면 단위로 놓친 곳이 없다.** 그 위에서 관리자가 지울 오탐 사진이 3분의 1로 줄었다.
- 주의: 이 숫자는 **사진 단위(있음/없음)** 입니다. 흠집 하나하나(인스턴스)나 크기별 재현율은 재지 않았으므로 "작은 흠집을 놓친다" 같은 말은 하지 않습니다.
- 학교 서버(고객 폰 사진, ONNX CPU)와 부스 Jetson(TensorRT)은 **언제나 같은 모델 버전**입니다. 출고와 수령을 다른 모델로 보면 "모델이 달라 흠집이 생긴 것처럼 보인다"는 분쟁이 생기기 때문입니다.

### 7-3. Jetson 추론

- jetson2에는 torch·ultralytics를 깔 수 없어(관리자 권한 없음, 메모리 7.3GB), **TensorRT 파이썬 + libcudart(ctypes) + numpy·OpenCV로 YOLO11-seg 후처리를 직접 짰습니다**(booth #25). ultralytics 결과와 마스크 IoU 0.86~0.99로 맞췄습니다.
- ONNX 조건을 학습 쪽과 고정했습니다: 입력 1×3×640×640 고정, opset 17, NMS·end2end 끔, 타일 640·겹침 0.2. 엔진은 Jetson에서 FP16으로 빌드합니다.
- **탐지 12장 2.53~2.63초**(목표 30초, 한도 60초). 촬영은 카메라를 매번 여닫던 것을 열어 둔 채 쓰게 바꿔 한 단계 약 5초 → 0.3~0.5초가 됐습니다(booth #61, 끄려면 `TRACE_BOOTH_KEEP_OPEN=0`).

### 7-4. 사람 검수 루프 (11/8)

```
AI 탐지(conf 0.25 이상, 넓게) → 후보 묶음(groupId)
  → 관리자 "검사 결과 → 검수하기": 흠집 맞음(CONFIRMED) / 흠집 아님(DISMISSED + 사유: 먼지·스티커·빛 반사 …)
  → 검수 완료 → 그때 등급 → 봉인(해시 체인)
  → reviews.csv → trace-ml review export → train --extra-train (확정 = 라벨, 흠집 아님 = 음성 예시)
```

- 남은 후보가 있으면 409 `REVIEW_PENDING_REMAINS`, 탐지가 아직이면 409 `REVIEW_NOT_READY`. 흠집 아님은 등급·고객 화면에서 빠지고 관리자 화면에만 점선으로 남습니다.
- 판정 이벤트를 1.3으로 올려 선택 필드 `review`만 더했습니다(계약은 추가만, report-server는 모르는 필드를 무시).
- 되돌림 스위치 `REVIEW_REQUIRED=false`(capture-server)를 둬, 검수가 시연을 막으면 예전처럼 탐지 직후 등급을 매깁니다.
- 바뀐 PR: contracts #32, capture_server #19·#20, gateway #12, web #87, booth #48, ml #28.

### 7-5. 진단 에이전트 한 줄 설치

```
macOS:   curl -fsSL https://gakdo.site/agent.sh | sh -s <페어링 코드>
Windows: & ([scriptblock]::Create((irm https://gakdo.site/agent.ps1))) <페어링 코드>
```

- gakdo.site 주소는 web nginx가 GitHub의 **고정 태그**(지금 macOS `agent.sh` v0.3.0, Windows `agent.ps1` v0.2.0) 스크립트로 302를 줍니다. 레포 클론·가상환경·pip 없이 `~/.trace-agent`에 풀고 `python -m trace_agent run`을 합니다.
- 실행 의존성은 jsonschema 하나라 `pip --target`으로 받습니다(학교 망 PyPI가 막히면 미러). 파이썬이 3.11보다 낮은 맥(기본 3.9)은 python-build-standalone 3.12를 **SHA-256을 고정해** 받고, `smartctl`이 없으면 smartmontools dmg에서 관리자 권한 없이 꺼냅니다(agent #10·#11).
- 읽는 명령·경로는 코드 상수로 고정(system_profiler·ioreg·smartctl·pmset / Get-CimInstance·powercfg). 결과를 contracts 진단 JSON Schema로 검증한 뒤 **먼저 보여 주고, y일 때만** 페어링 JWT로 올립니다(FR-DIA-05, 서버에 `consented_at`).
- 실기: 민서 맥, 친구 MBA(파이썬 3.9뿐), 윈도우 갤럭시북에서 설치·수집 확인(11/9·11/10).

## 8. 예상 질문과 답

### 일정·범위

**Q. 50개 요구사항을 2주에 다 했다는 게 믿기지 않는다. 어떻게 관리했나?**
A. 세 가지입니다. ① 11/3 계약 고정으로 레포 15개가 서로 기다리지 않고 동시에 갔습니다. ② 같은 날 "끝까지 도는 흐름 하나 먼저"로 순서를 바꿔 11/9에 시연 가능한 상태를 먼저 만들었습니다. ③ 완료 기준을 "머지"가 아니라 "실기·배포 확인"으로 잡아 시트 D열에 그것만 체크했습니다. 끝까지 못 한 것(클러스터, InfluxDB·Grafana, 3DGS 등)은 [requirements.md](requirements.md)에 그대로 적었습니다.

**Q. 프리즈 뒤에도 PR이 있는데 프리즈가 맞나?**
A. 11/13 이후 머지는 문서·README·SonarQube 정리와 11/20 리뷰 준비분뿐입니다(decisions.md 11/13). 11/20 리뷰 준비분은 정규화 1단계(삭제 없는 변경), CI 커버리지 관문, gateway 오류 응답 형식(뒤쪽 서버 연결 실패를 500 기본 JSON 대신 503 Problem으로, gateway #27)입니다. 새 기능은 넣지 않았고, 정상 응답·재시도 규칙도 그대로입니다.

### 브랜치·배포

**Q. Git Flow라면서 develop이 운영에 나간다. 그럼 main은 왜 있나?**
A. 맞습니다. 처음 설계는 main = 클러스터 배포였는데, 11/3 클러스터를 멈추고 학교 서버 Compose로 바꾸면서 서버가 `:develop`을 받아 배포하게 됐습니다. 그 뒤 main은 릴리스 태그·CHANGELOG 기록 용도로만 남았습니다. 실서버 확인을 하루에 여러 번 해야 해서 택했고, 대신 배포마다 커밋 SHA 확인·자동 되돌리기·시연 전 일시 정지를 넣었습니다. 다시 한다면 develop은 스테이징, main은 운영으로 나누겠습니다.

**Q. 배포가 실패하면?**
A. autodeploy가 새 컨테이너를 옆에 띄워 180초 안에 ping과 커밋 SHA를 확인하고, 안 되면 새 컨테이너만 지우고 그 이미지를 '실패'로 적습니다. 운영 중인 옛 컨테이너는 그대로라 끊기지 않습니다(web만 포트 때문에 1~2초). Discord로 알림이 옵니다.

**Q. DB 마이그레이션은 어떻게 안전하게 하나?**
A. Flyway로 서버마다 자기 스키마만 다루고, 머지된 파일은 고치지 않고 새 파일만 더합니다. 자동 되돌리기는 코드만 되돌리므로 헌법에 "컬럼 추가 먼저, 삭제는 다음 배포"를 두었고, 11/20 정규화도 1단계(쓰지 않기·제약 추가, NOT VALID 뒤 확인)와 2단계(DROP)로 나눴습니다([erd.md](erd.md)).

### PR·리뷰

**Q. 승인 0명이면 리뷰를 안 한 것 아닌가?**
A. 세 명이 레포를 나눠 맡아 같은 코드를 동시에 보는 일이 드물었고, 사람 승인을 기다리면 하루씩 밀렸습니다. 그래서 사람 승인 대신 기계 관문을 강하게 했습니다: 필수 검사(테스트·커버리지·gitleaks·계약 린트), CodeRabbit 자동 리뷰(심각한 지적은 머지 전에 고침), 계약 PR은 팀 공지 후 먼저 머지. 약점은 맞고, 팀이 커지면 계약·보안·마이그레이션 PR만이라도 1명 승인을 필수로 하겠습니다.

**Q. AI가 코드를 다 짰으면 팀이 이해하고 있나?**
A. 원칙(헌법·CLAUDE.md·컨벤션), 결정(decisions.md), 확인(실기)은 사람이 했습니다. AI가 계약을 바꿔야 할 때는 코드를 고치지 말고 멈추게 했고, Spec Kit으로 명세 → 계획 → 작업을 문서로 남겨 왜 그렇게 짰는지 추적할 수 있습니다. 모델 선택(v004), 사람 검수 도입, Compose 전환 같은 판단은 모두 결정 기록에 사람 이름으로 남아 있습니다.

### 테스트

**Q. 커버리지 40%는 너무 낮지 않나?**
A. 40%는 관문(이 아래면 머지 불가)이고, 실제는 자바 60~98%, 웹 89%, 파이썬 82~92%입니다. 처음부터 높게 걸면 뼈대 단계에서 CI가 막혀 40%로 시작했습니다. 11/20에 파이썬 레포에도 70% 관문을 더했습니다. 가장 낮은 report_server(약 60%)가 다음 보강 대상입니다.

**Q. Testcontainers 테스트를 로컬에서 건너뛰면 의미가 있나?**
A. 개발 세션(클라우드)에는 Docker가 없어 건너뛰고, GitHub Actions에서는 반드시 돕니다(필수 검사). 그래서 DB 제약 같은 핵심 규칙은 Docker 없이 도는 단위 테스트로도 한 번 더 덮습니다.

**Q. 하드웨어(카메라·Jetson·노트북)는 어떻게 테스트했나?**
A. 장치 호출을 함수 하나로 감싸 테스트에서 가짜로 바꿉니다(가짜 카메라, 실제 기기에서 받은 명령 출력 고정 파일). 부스는 가짜 카메라로 서버를 띄워 Chromium으로 화면을 눌러 보는 하네스까지 CI에서 돕니다. 실제 장치는 실기로 확인하고 결과를 스탠드업·시트에 남겼습니다(jetson2 926장 해시 일치 등).

**Q. Jetson은 Python 3.10인데 CI는 3.12다.**
A. 지금까지는 ruff `target-version = "py310"`으로 문법만 막았습니다. 11/20에 실제 3.10으로 테스트를 도는 잡을 더했습니다(booth #71, 로컬 3.10에서 264개 통과 확인).

### B 기술 흐름

**Q. 검증 데이터는 어떻게 나눴나? 누수는?**
A. 사진이 아니라 기기 단위로 나눴습니다(15대 중 3대를 통째로 검증). 같은 노트북 사진이 양쪽에 있으면 같은 흠집을 외운 것을 성능으로 착각합니다. 100에포크 실험에서 학습 기기를 외우는 현상이 실제로 나와 2에포크 미세조정을 택했습니다.

**Q. mAP를 안 쓴 이유는?**
A. 흠집이 적은 부스 데이터에서는 mAP가 폴리곤 모양·클래스까지 따져 실제 판정과 따로 놀았습니다(v001 mAP50 0.184인데 면 판정 6/6). 서비스가 내는 결과는 "이 면에 흠집이 있나"라서 그것을 세는 평가기를 만들었습니다.

**Q. 재현율이 0.77에서 0.60으로 떨어졌는데 왜 v004인가?**
A. 같은 검증셋·같은 conf 0.25에서 v002 증강과 비교한 숫자입니다. 오탐 사진이 48장에서 15장으로 줄고 흠집 있는 면은 4/4를 모두 잡았습니다. 사람이 검수하는 구조라 관리자가 지울 오탐이 적은 쪽이 운영에 맞다고 봤습니다. 사진 단위 숫자라 크기별 놓침은 재지 않았습니다.

**Q. 검수 결과는 다시 학습에 쓰나?**
A. 네. 관리자가 확정한 흠집은 라벨, 흠집 아님은 음성 예시로 `trace-ml review export` → `train --extra-train`에 넣는 흐름을 만들었습니다(ml #28). 대회 전에는 v004를 바꾸지 않기로 해서 그 흐름으로 학습한 모델을 배포하지는 않았습니다.

**Q. `curl | sh`는 보안상 위험하지 않나?**
A. 위험을 줄인 장치: HTTPS만, 스크립트는 고정 태그(macOS v0.3.0·Windows v0.2.0)에서만 받고, 내려받는 파이썬·smartctl은 SHA-256을 고정해 검증, 관리자 권한을 쓰지 않으며, 업로드는 결과를 보여 주고 동의한 뒤에만 합니다. 남은 약점은 스크립트가 받는 에이전트 소스 자체의 체크섬·서명이 없다는 것으로, 11/11 CodeRabbit 리뷰(agent #14)에서도 같은 지적을 받았습니다. 그래서 다음에는 릴리스에 체크섬·서명을 함께 게시하겠습니다.

**Q. 학습과 추론 환경이 다른데(ultralytics vs TensorRT 직접) 결과가 같다고 어떻게 보장하나?**
A. 같은 ONNX 조건(입력 고정·opset 17·NMS 끔)으로 내보내고, 같은 사진으로 ultralytics와 마스크 IoU 0.86~0.99를 확인했습니다. 학교 서버(ONNX CPU)와 Jetson(TensorRT)도 같은 파일로 함께 바꿉니다.
