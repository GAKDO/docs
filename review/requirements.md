# 리뷰 준비: 요구사항

11/20 강사님 전체 리뷰(요구사항·스펙·ERD·아키텍처·API·개발 과정) 중 **요구사항** 파트 준비 문서입니다. 자세한 근거 표는 [../design/requirements-status.md](../design/requirements-status.md)(요구사항별 상태·구현 위치), 결정 이유는 [../decisions.md](../decisions.md)에 있습니다.

## 30초 요약

- 요구사항은 **50개(기능 44 + 비기능 6)**, 10/30 설계서([../design/mvp-design.md](../design/mvp-design.md))에서 정했고 모두 "필수"입니다. 이것을 레포별 **기능 27개**([../speckit/backlog.md](../speckit/backlog.md))로 나눠 Spec Kit으로 만들었습니다.
- 11/20 기준 **44개는 수용 기준까지 확인(✅)**, 5개는 일부(◐), 1개는 API만 있고 화면을 숨김(⏸)입니다. 표 밖 선택·실험 2개(검색, 3DGS)는 하지 않았거나 일부만 했습니다.
- 11/3 강사님 리뷰로 **요구사항을 지우지 않고 순서만 바꿨습니다**: "부스 12장 → Jetson 판정 → 관리자 화면"을 먼저 끝까지 돌리고, 해시 체인·폰 수령·진단을 하나씩 다시 넣었습니다. 끝까지 뺀 것은 클러스터, InfluxDB·Grafana, 파일럿 등록 화면, Elasticsearch, 3DGS입니다.
- 11/6 이후 리뷰·시연 준비 중에 표 밖 기능 12개가 생겼습니다(사람 검수, 반납 정산, 공개 노트북 목록, 소셜 로그인, 챗봇 등). 모두 계약을 **추가만** 하는 방식으로 넣었습니다.

## 요구사항이 코드까지 가는 흐름

```
렌탈 분쟁 시나리오(출고·수령·반납에서 "이 흠집 언제 생겼나")
  → 설계서 요구사항 50개 (ID · 도메인 · 요구사항 · 측정 가능한 수용 기준 · 담당)     10/30
  → 리뷰 결정 14건 (SSD 필수 여부, 3D 방식, 인증 방식 …)                        10/30
  → 레포별 기능 27개 + 의존 순서·마감 (speckit/backlog.md)                        11/1
  → 레포마다 /speckit-specify → clarify → plan → tasks → analyze → implement → converge
       = specs/<번호>-<이름>/spec.md·plan.md·tasks.md
  → 계약 고정 contracts 1.0.0 (OpenAPI 5개, 진단 JSON Schema, 이벤트, codes.yaml)   11/3
  → PR (본문에 백로그 ID·요구사항 ID·테스트 방법), 테스트 이름 = 수용 기준 문장
  → 감사: 구현현황 시트(세부 기능 단위) + requirements-status.md(요구사항 단위)    11/8, 11/20
```

수용 기준이 실제 장치로 이어진 예:

| 요구사항 | 수용 기준 | 지키는 장치 | 확인 |
| --- | --- | --- | --- |
| FR-RNT-01 | 같은 시리얼로 진행 중 렌탈 2건이 생기지 않는다 | DB 부분 유니크 인덱스 `ux_rental_open_device`(애플리케이션 검사가 아니라 DB가 막음) | 동시 생성 10건 중 1건만 성공(Testcontainers PostgreSQL) |
| FR-RNT-02 | 출고 전에 수령 기록을 만들면 거부 | 앞 시점이 SEALED가 아니면 409 | 단위·통합 테스트, 11/9 실서버 세 시점 완주 |
| FR-AUTH-03 | 역할 × 경로 표의 모든 칸이 테스트로 확인 | 계약 operation마다 `x-trace-access` → gateway `access-policy.yaml` 생성 | `RoleRouteMatrixIntegrationTest`(경로 × 역할 전부) |
| FR-CAP-02 | 내려받은 파일 해시 = 저장된 해시 | 사전 서명 URL에 SHA-256 체크섬 헤더 서명, 완료 때 저장소 해시 대조 | jetson2 926장 `shots --verify` 전부 일치 |
| FR-INT-01 | 사진 한 장을 바꾸면 검증 실패 | 정규화 JSON → SHA-256 → 앞 줄 해시 연결, Ed25519 서명, 검증 때 MinIO 사진 재해시 | 변조 탐지 테스트(`valid=false`, `brokenSeq`) |
| FR-DIA-05 | 동의 없이는 전송되지 않는다 | 에이전트가 결과를 먼저 보여 주고 y일 때만 업로드, 서버에 `consented_at` | 가짜 서버 테스트, 11/6 실서버 업로드 |

## 예상 질문과 답

### 도출·범위

**Q1. 요구사항 50개는 어떻게 뽑았나요?**
렌탈 업체와 고객이 반납 때 다투는 상황("이 흠집은 원래 있었다")에서 출발했습니다. 세 시점에 같은 기준으로 기록하고(촬영·검사·진단), 기록이 바뀌지 않았음을 증명하고(무결성), 고객이 직접 본다(회원·리포트)로 도메인 11개를 나눴습니다. 진단 JSON은 다른 서비스 조사를 거쳤고([../design/diagnostics-json-v0.md](../design/diagnostics-json-v0.md)), 10/30 강사님 리뷰에서 기기 관리의 빈 곳을 지적받아 FR-RNT-05(기기 목록·상태)를 더했습니다.

**Q2. 50개가 모두 "필수"면 우선순위가 없는 것 아닌가요?**
맞는 지적입니다. 10/30에는 "일정이 밀려도 빼지 않는다"로 정해서 우선순위 칸이 의미가 없었습니다. 실제 우선순위는 11/3 단계표(MVP → 2단계 → 3단계 → 중단)가 했습니다. 다시 한다면 처음부터 MoSCoW로 나누고, "세 시점 한 바퀴"에 꼭 필요한 것만 Must로 두겠습니다.

**Q3. 11/3에 범위를 왜, 어떻게 줄였나요?**
기능 27개를 동시에 만들면 11/10에 어떤 흐름도 끝까지 돌지 않을 위험이 컸습니다. 그래서 끝까지 도는 가장 작은 흐름(부스 12장 → Jetson 판정 → capture-server 등급 → 관리자 화면)을 먼저 띄우고, 그 위에 해시 체인(11/4), 진단(11/6), 폰 수령·리포트(11/8)를 다시 얹었습니다. 요구사항은 지우지 않고 순서만 바꿨고, 11/9에 세 시점을 완주했습니다.

**Q4. 결국 요구사항을 몇 개 지켰나요?**
50개 중 44개는 수용 기준까지 확인했습니다. 나머지 6개와 이유:
- FR-INS-02 정합: SuperPoint + LightGlue 보정까지 코드는 있지만, 실사진 폰↔부스 정합 오차 측정이 없습니다(합성 사진만).
- FR-PIL-01·02 파일럿: 참여자 별칭 등록은 API만, 추이는 Grafana 대신 기기 단위 '성능' 화면입니다.
- NFR-01 30초: 탐지만 12장 2.53초로 쟀고, 촬영부터 저장까지 10회 평균·최대는 재지 않았습니다.
- NFR-03 비밀·키: gitleaks는 통과하지만, 서비스별 DB·MinIO·RabbitMQ 계정 분리는 대회 뒤로 미뤘습니다.
- NFR-05 클러스터 자가 복구: 클러스터를 쓰지 않고 Compose 재시작·자동 되돌리기로 대신했습니다.

**Q5. 요구사항에 없는 기능을 왜 이렇게 많이 넣었나요? 범위가 번진 것 아닌가요?**
일부는 그렇습니다. 다만 대부분 앞 요구사항의 위험을 막으려고 생겼습니다. 사람 검수(X-01)는 증강 모델이 먼지·테이프 반사를 흠집으로 잡아 AI만으로 청구되는 경로를 막으려고, CAM1·CAM2 묶기(X-02)는 같은 흠집이 두 번 세어져 등급이 올라가는 문제 때문에, 반납 정산(X-05)은 "반납 때 무엇을 청구하나"가 비어 있어서 넣었습니다. 소셜 로그인·챗봇·MCP는 시연 매력을 위한 것이라 순수한 추가입니다. 모두 계약을 추가만 해서 기존 클라이언트를 깨지 않았습니다. 아쉬운 점은 이 12개를 설계서 요구사항 표에 ID로 올리지 않고 PR과 decisions.md에만 남긴 것입니다.

### 수용 기준·추적성

**Q6. 수용 기준을 어떻게 확인했나요?**
수용 기준을 측정 가능한 문장으로 쓰고(예: "동시 생성해도 진행 중 렌탈이 2건 생기지 않는다"), 서버 테스트 이름을 그 문장으로 짓는 것이 컨벤션입니다. DB가 걸린 기준은 Testcontainers로 실제 PostgreSQL·RabbitMQ에서 돌리고(Docker 없는 곳에서는 건너뜀, GitHub Actions에서 돔), 실기로만 확인되는 것(해시 일치, 메일 수신, Jetson 시간)은 날짜와 함께 시트·보드에 남겼습니다.

**Q7. 요구사항 하나에서 코드까지 어떻게 찾아가나요?**
requirements-status.md의 요구사항 행 → 백로그 기능(예: RE1) → 레포 `specs/001-rental-device-checkpoint/` → PR(본문에 FR-RNT-01) → 코드 경로 순입니다. 빈 곳도 있습니다: RP2(SSE)는 별도 명세가 없고, 명세 번호가 겹치거나 빈 곳이 있으며(web `003-*` 두 개, diagnostics `002` 없음), 11/8 이후 추가 기능은 명세가 없습니다.

**Q8. 요구사항이 바뀌면 어떻게 관리했나요?**
세 군데에 남깁니다. ① decisions.md에 날짜·누가·왜, ② 계약이 바뀌면 contracts에 추가만 하는 PR(1.0.0 고정 뒤 이벤트 1.1 → 1.3처럼 선택 필드만), ③ 보드·시트 갱신. 레포 규칙상 계약을 바꿔야 하면 코드를 고치지 않고 멈추고 사람에게 알립니다(11/10부터 소셜 로그인·챗봇·MCP만 예외).

**Q9. 시트는 다 TRUE인데 문서는 44/50이라 다릅니다.**
보는 단위가 다릅니다. 시트는 "그 세부 기능이 돌아가는가"(예: '파일럿 추이 대시보드' 화면 행), 문서는 "요구사항의 수용 기준을 확인했는가"입니다. 그래서 FR-PIL-02는 시트에서는 화면 기준 TRUE, 문서에서는 Grafana 대신 다른 화면이라 ◐입니다.

### 기능 요구사항의 근거

**Q10. AI가 오탐하면 고객이 억울하게 청구되지 않나요?**
그래서 11/8에 "AI는 후보를 넓게 잡고 사람이 확정한 것만 등급·정산에 쓴다"로 바꿨습니다(X-01). AI 혼자 청구까지 가는 경로는 없습니다. 반대로 놓친 흠집은 관리자가 직접 그려 넣고(source = HUMAN), 확정·기각 결과는 다음 학습의 양성·음성 예시가 됩니다(재학습 파이프라인 X-03). 대회 모델 v004는 검증 기기 3대에서 흠집 있는 면 4/4를 찾았고 사진 정밀도 0.71, 사진 재현율 0.60입니다([../contest/metrics/M3.md](../contest/metrics/M3.md)).

**Q11. 흠집 4종(긁힘·찍힘·균열·오염)이라 했는데 실제로 다 학습했나요?**
모델 클래스는 4종이지만, 빌린 MacBook Air 15대에서 나온 라벨은 찍힘 541개·긁힘 187개이고 균열·오염은 없습니다. 사실상 2종을 학습했고, 부스 데이터에 균열·오염 예시가 없어 그 두 종은 검증하지 못했습니다. 오염은 등급에서도 뺍니다(FR-INS-04).

**Q12. 해시 체인이 왜 요구사항에 있나요? DB에 저장하면 되지 않나요?**
분쟁에서 기록을 가진 쪽(업체)이 나중에 고칠 수 있으면 증거가 되지 않기 때문입니다. 사진·진단 JSON 해시를 앞 기록 해시에 잇고 서버 Ed25519 키로 서명합니다(FR-INT-01). 그래도 업체가 체인을 통째로 다시 만들 수 있으니, 봉인 순간의 지문을 고객 메일로 보냅니다(FR-INT-03 봉인 영수증). 고객이 가진 지문과 검증 페이지 지문이 다르면 조작입니다.

**Q13. 진단 결과는 사용자가 조작할 수 있지 않나요?**
어느 시점·어느 기기의 진단인지는 본문이 아니라 페어링 JWT(5분·1회용)에서 서버가 정하고, 본문 시리얼이 렌탈 기기 시리얼과 다르면 422입니다. 원본 JSON과 SHA-256을 저장하고 봉인 뒤에는 바꿀 수 없습니다. 다만 에이전트 출력 자체에 서명이 없어, 에이전트를 고쳐 가짜 값을 보내는 것까지는 막지 못합니다. 그래서 진단은 "점검 플래그"(부품 변경·용량 급감 등)로 사람이 다시 보게 하는 근거로 씁니다.

**Q14. 수령은 왜 부스가 아니라 폰인가요?**
수령은 고객이 집에서 받는 순간이라 부스가 없습니다. 대신 폰 웹앱이 면마다 윤곽 가이드를 띄우고 블러·반사를 검사해 불량이면 제출을 막고(FR-CAP-03), 그래도 품질이 낮은 면은 "판정 불가"로 두고 비교·등급에서 뺍니다(FR-CAP-04). HTTPS가 없으면 브라우저가 카메라를 막아서 도메인 구매가 이 요구사항의 전제였습니다.

**Q15. 빠른 검사(12장)와 전체 검사(28장)를 섞으면 비교가 되나요?**
안 됩니다. 그래서 11/13에 수령·반납은 출고와 같은 검사 방식만 받게 막았습니다(contracts #49). 빠른 검사는 기기 놓는 자리가 매번 달라 위치 비교가 없으므로, 반납 정산은 면·종류별 흠집 수가 늘어난 만큼만 신규로 봅니다.

### 비기능 요구사항

**Q16. NFR-01 30초는 어디서 나온 숫자인가요?**
설계서에는 30초의 근거 문장이 따로 없습니다(답할 때는 "부스 앞에서 직원·고객이 기다리는 시간"으로 설명). 11/5 합성 모델로 12장 약 49초가 예상돼 목표 30초·한도 60초로 정했고, 대회 모델 v004 TensorRT FP16 엔진으로 탐지만 12장 2.53초가 나왔습니다. 촬영 단계는 카메라를 열어 두는 개선(booth #61)으로 단계당 약 5초에서 0.3~0.5초로 줄였습니다. 촬영부터 저장까지 10회 평균·최대는 아직 재지 않았습니다.

**Q17. 성능·가용성 요구사항이 적습니다. 동시 사용자 수 같은 건요?**
맞습니다. 업체 규모(하루 처리 대수, 동시 접속)를 가정하지 않아 처리량 요구사항이 없습니다. 지금 있는 것은 남용 방지(로그인·가입·재설정 IP 분당 10회, 공개 목록 IP당 300회)와 장애 대응(Compose 재시작, 자동 배포 실패 시 자동 되돌리기, 야간 백업)입니다. 다음 단계라면 "부스 1대 하루 N대, 검수 대기 M분 이내" 같은 운영 기준을 먼저 정하겠습니다.

**Q18. 개인정보는 요구사항에서 어떻게 다뤘나요?**
수집은 이메일·이름만(설계서 "제외" 항목), 탈퇴하면 이메일·이름을 지우고 렌탈 기록은 익명으로 남깁니다(FR-USR-04). 에이전트는 읽는 명령 목록을 코드 상수로 고정하고 컴퓨터 이름·UUID를 보내기 전에 지웁니다(NFR-02). 화면에서는 시리얼을 뒤 4자리만 보이고, 챗봇이 외부 모델(Gemini)로 보내는 시리얼도 뒤 4자리만 남깁니다.

**Q19. 클러스터에 올린다고 했는데 왜 Compose인가요?**
11/3 재조정에서 클러스터 비밀·Argo CD를 갖추기 전에 학교 서버 Compose와 강사님 nginx(HTTPS)로 바로 띄워 흐름부터 확인하기로 했습니다. NFR-05(파드 자가 복구)는 그래서 ◐이고, 대신 컨테이너 재시작 정책, 무중단 교체와 실패 시 자동 되돌리기, 야간 백업으로 "스스로 복구"의 뜻을 살렸습니다. 쿠버네티스 매니페스트는 gitops에 남겨 CI로 계속 검증합니다.
